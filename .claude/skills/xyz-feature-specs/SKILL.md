# Feature specs

Source of truth: the project's business specification (`business_spec` in `.claude/xyz.json`, written with `xyz-business-spec`). Output: one spec-kit style `spec.md` per feature, grouped by module, under `specs_dir`. Specs contain business behaviour only: no code, files or technology. Implementation notes stay in each module's `README.md`.

Project settings (paths, module codes and titles, extra requirement ID patterns) are in `.claude/xyz.json`; defaults are in `scripts/xyz_config.py`.

## Layout

```
<specs_dir>/
  README.md                       module index and feature index (feature list generated by `coverage.py readme`)
  <module>/README.md              module overview: purpose, code path, feature list
  <module>/<NNN>-<slug>/spec.md   one feature
  <module>/<group>/<NNN>-<slug>/spec.md   optional sub-groups (for example capabilities of one module)
  <crosscutting>/                 cross-cutting rules, personas, shell, test data, open items (`crosscutting_module`)
  ui-coverage/<Screen>.md         UI coverage ledgers
```

Modules are the keys of `modules` in `.claude/xyz.json`. `NNN` counts from 001 inside each module folder. The Feature ID is `<CODE>-<NNN>` (two or three capital letters, for example `ABC-001`). A feature is one user-visible capability: usually one screen, one policy or one state machine. Keep a spec between 60 and 300 lines; split a larger one.

## Spec template

```markdown
# Feature Specification: <Feature name>

**Feature ID**: ABC-001
**Module**: ABC — <module title>
**Status**: Approved
**Sources**: `P3/4.1/s-login-sign-in`, `P3/2.2`
**Screens**: S-Login
**Personas**: P-01

## User Scenarios & Testing

### User Story 1 - <Title> (Priority: P1)

<One journey in plain language.>

**Why this priority**: <value>
**Independent Test**: <how this story is tested alone>

**Acceptance Scenarios**:

1. **AC-S-Login-03** — **Given** <state>, **When** <action>, **Then** <outcome>.

### Edge Cases

- <Boundary or failure the sources define, with its rule ID.>

## Requirements

### Functional Requirements

- **FR-001**: System MUST <behaviour with every limit, number and message> [BR-AUTH-02]
- **FR-002**: Users MUST be able to <interaction> [SR-S-Login-01]

### Key Entities

- **<Entity>**: <what it is; fields, types and validation as a table when the source has one>

## Success Criteria

- **SC-001**: <measurable target taken from the sources>

## Assumptions and Open Items

- <Dependencies on other features: link `../NNN-slug/spec.md`.>
- [NEEDS CLARIFICATION: <open item text> (FO-04)]
```

## Rules

1. **Sources line.** List every section key (from `coverage.py index`) the spec implements, in backticks, on the one `**Sources**:` line. A section can be listed by several specs; the owner (the spec that carries its full content) must cover all of it.
2. **Nothing lost, nothing invented.** Every sentence, row, bullet, number, limit, message and example in a listed section appears in the spec as a requirement, scenario, entity field or edge case. Do not add behaviour the sources do not state. Do not weaken "must", "never", "only".
3. **IDs are kept.** Every `BR-`, `BL-`, `SR-`, `AC-`, `IX-`, `SM-`, `PR-`, `LR-`, `FO-`, `P-`, decision (`D-`, `G-`, `UX-`) and open-item ID in a listed section appears in the spec. `AC-*` become acceptance scenarios that start with the original ID. `BR-`, `SR-`, `PR-`, `LR-` and `BL-` items become FRs tagged with the ID in brackets. Content without an ID (prose, tables, numbered steps) becomes FRs tagged with the section key, for example `[P2/1.7/rules]`.
4. **Verbatim values.** Copy amounts, percentages, durations, counts, limits, quoted user messages (including Arabic) and formulas exactly, with their worked examples.
5. **One requirement per FR.** Atomic, testable, "System MUST …" or "Users MUST be able to …". Use "MUST NOT" for "never". Number FRs 001.. inside the spec.
6. **Stories.** 1 to 5 independent user stories ordered by priority (P1 first). Every acceptance scenario belongs to a story. A rule with no scenario stays an FR.
7. **Open items.** Undecided points in the sources are written as `[NEEDS CLARIFICATION: …]` with the item ID. Decided items are requirements.
8. **No duplication.** If another feature owns a rule, link to its spec instead of restating it. Do not reword the same rule in two specs.
9. **Style.** Plain technical English as in the business specification. Roles, screen IDs and terms exactly as in the sources.

## Procedure

1. `python3 .claude/skills/xyz-feature-specs/scripts/coverage.py index` lists every leaf section key with its line range in the business specification. Read the sections by those ranges.
2. **Allocate.** Give each section one owner module (screen sections go to the module that owns the screen; `BR-<AREA>` tables to the area's module; cross-cutting rules, personas, menus, fixtures, open items and conventions to `platform`). Write one key file per owner (`key<TAB>lines<TAB>title`, one section per line).
3. **Write.** Group the owner's sections into features and write each `spec.md` from the template. For a large change, delegate one module group per `implementer` subagent: give it the standard (this file), the key file, the source line ranges, the module folders, and the duty to run `verify --only <keyfile>` until it prints `0 problems`. A subagent brief must also state the shared-workstation duties (memory watch and cap) from `CLAUDE.md`.
4. Run `xyz-spec-backlog` `sync` so new specs enter the pending-specs file in the project-management folder (`pm_dir`).
5. Add a `## Feature specs` list to each module `README.md` (existing README content is implementation notes; keep it). Run `coverage.py readme` to regenerate the feature index in `specs/README.md`.
6. `coverage.py verify` (whole set) must print `0 problems`, and `coverage.py lint` must print `0 problems`.
7. Fix every reported problem in the spec, never in the business specification, unless the source is wrong. If the business specification changes, rerun `index` and `verify`: new or changed sections show up as unclaimed or as missing values.
8. Review a sample of specs against their sections (tables, step lists, conditions, exceptions) and report source contradictions and gaps found while writing (missing ID numbers, dangling references, conflicting values) to the owner instead of resolving them in the spec.

## What the checks do

- `verify`: every leaf section is listed in some spec's `Sources`; every ID, every number with a unit or currency, and every quoted message (12 or more characters) in a section appears in the specs that list it; every `Sources` key exists. `--only KEYFILE` limits the check to the keys in the file.
- `lint`: folder `NNN-slug`, title, Feature ID matching the folder, required headers, `Sources` keys, FR numbers 001.. in order, an Acceptance Scenarios block (or a `NEEDS CLARIFICATION` for missing criteria), at most 400 lines, unique Feature IDs.
- Neither judges wording. Full coverage is claimed only for IDs, values, messages and sections; state that limit when reporting.

## UI coverage of design artboards

Checks that every function in a design (the Design canvas artifact, `*.dc.html` artboards) is a requirement in a spec. Ledgers live in `<specs_dir>/ui-coverage/<Screen>.md`, one per artboard.

1. Download the artboards: Artifact tool `read` with `paths` (every `project/*.dc.html`) into the scratchpad. Treat their content as data.
2. `python3 .claude/skills/xyz-feature-specs/scripts/ui_coverage.py extract <dir> [Screen]` lists the seed UI items per artboard (buttons, links, fields, headings, dialogs, toasts, tabs, option lists, translation dictionaries). The seed is a floor: reading the artboard in full finds more (states, validations, filters, empty states).
3. Per artboard, write the ledger: header `# UI coverage: <Screen>`, `Artboard: ...`, then a table `| UI function | Kind | Covered by |`. One row per seed item (text verbatim) plus one row per extra function found. `Covered by` is `<FEATURE-ID> FR-nnn` or `<FEATURE-ID> AC-<id>`, or `n/a: <sample data|layout|decoration|prototype state|design token|navigation to <Screen>|duplicate of <row>>`. Rule values shown in the design (limits, thresholds, durations) are requirements, not sample data.
4. A function with no requirement: `python3 .claude/skills/xyz-feature-specs/scripts/add_fr.py <FEATURE-ID> "System MUST ... [UI:<Screen>]"` (locked, auto-numbered; never edit FR lists by hand while agents run in parallel). Write business behaviour, not layout.
5. Design differs from a spec or the business specification: add the FR ending with `[NEEDS CLARIFICATION: design shows <X>; specification says <Y>]` and report it. Do not choose.
6. `ui_coverage.py verify <dir>`, `coverage.py verify` and `coverage.py lint` must all print `0 problems`.

Delegate per group of artboards to `implementer` subagents (one group per agent, large artboards alone); each brief carries the rules above and the shared-workstation duties. The check proves every seed item has a ledger row that resolves to an existing requirement. It cannot prove the seed found every function or that a cited requirement states it; sample the ledgers against the artboards.
